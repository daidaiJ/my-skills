# Stage 1 — 信号收敛与代码对照

> 由 SKILL.md 阶段路由加载。本轮目标：交叉验证，根因逐步逼近。

## 信号标注

对每个新线索标注：**证据强度**（S0 猜测 / S1 单一证据 / S2 可复现 / S3 已量化）× **影响面**（用户感知 × 频率 × 范围）。

## 交叉验证规则

- **两个以上独立线索指向同一位置 → 升级为候选问题**（进 hypotheses，标置信度）
- 信号越多、越独立（不同来源，非同一日志的重复行），置信度越高
- 单线索不升级——留在 clues/ 待更多证据

## 代码对照（优先动作）

每个新线索落库后，**立即用代码搜索工具对照实现**（grep / codegraph / read_file），确认或排除：

- 线索指向的代码路径是否真的存在？调用链是否如日志所示？
- 实现是否与现象吻合（如日志报超时，代码里该处是否真有无界等待）？
- 对照结论写入线索文件或 facts.md（附代码位置）——这是把"现象"变成"缺陷"的关键一步

## 根因逐步逼近

facts.md 中每条根因/确认项带三个字段：**置信度（%）/ 支撑证据（线索编号列表，追加不删除）/ 最近核实**。

每轮反馈更新置信度：新证据支撑则升级，矛盾证据则降级并记录矛盾线索。状态机：`候选 → 部分验证 → 高置信 → 最终根因`。

**最终根因判定（三重确认，缺一不可）**：

1. **多源独立信号指向同一处**（线索交叉验证）
2. **代码对照确认**实现与根因吻合
3. **与所有已知反馈无矛盾**（含用户核实）

宣告"最终根因"后才可进入决策阶段。之后若出现新反馈，根因结论允许被重新评估——**结论可推翻，历史不可改**。

## 本轮结束检查

- [ ] 新线索已代码对照（结论落盘，附代码位置）
- [ ] 候选清单排序更新（证据 × 影响）
- [ ] 根因收敛 → 路由 stage-2；未收敛 → 说明缺什么信号，等下一轮反馈
