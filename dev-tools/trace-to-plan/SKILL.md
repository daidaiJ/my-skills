# Trace to Plan — 从痕迹到计划

**定位**：wayfinder 的反向。wayfinder 从目标自顶向下规划（空白工程，决策 tickets 地图 → 逐票解决）；本 skill 从现状自底向上发现（存量系统）——多边信号 → 收敛候选 → 验证决策 → 方案规划 → bench 闭环。

空白工程极少，存量改造是常态。本 skill 回答三个问题：

1. **哪里有坑** — 多源信号交叉收敛出高置信候选问题
2. **值不值得修** — ROI 决策，不是发现的问题都该修
3. **怎么修最顺** — 排序、依赖、验证方式齐备、贴合业务约束的实施计划

## 工作模式：多轮重入

**性能与设计缺陷定位天然是多轮的**：现象往往跨天出现，日志分批拿到，指标需要等待观测窗口，代码对照在每轮新证据后都要重做。因此本 skill 以**轮次（session）**为单位推进，每轮结束时状态沉淀到 `.issue/` 目录，下一轮从目录恢复继续——不重来、不丢失。

```
入口：读 .issue/（有则恢复，无则初始化）→ 接收本轮输入 → 记录线索
  ↕   （可反复多轮）
轮次：收集 → 追加线索 → 代码对照 → 更新事实/推断 → 检查收敛
收敛：验证决策 → 业务对齐方案 → 实施计划 → bench 闭环
```

每轮必须做且只做两件事：**追加新线索**、**更新事实/推断状态**。绝不重写已有线索——历史证据是调查的可信基础。

## .issue/ 目录约定

调查状态存于项目根 `.issue/`（或用户指定目录）。多问题并行时用子目录：`.issue/<slug>/`。

```
.issue/
├── index.md            # 索引摘要（每轮唯一必读）：时间线 + 状态 + 下一步 + 入口指针
├── issue.md            # 问题主档：现象描述、业务影响、当前状态
├── clues/              # 线索链：每条证据一个文件，递增编号，只追加
│   ├── 001-user-report.md       # 现象描述（用户原话/issue 摘录）
│   ├── 002-error-log.md         # 日志/trace 证据（原始行 + 时间窗口）
│   ├── 003-metrics.md           # 指标证据（数值、趋势、对比基线）
│   └── 004-code-spot.md         # 代码位置证据（文件:行 + 实现摘录）
├── facts.md            # 已确认事实（可复核，每项带来源线索编号）
├── hypotheses.md       # 推断与候选问题（标置信度，与事实严格分离）
├── decisions.md        # 决策记录（修/不修/延后，ADR 格式）
└── plan.md             # 实施计划（可重放修复步骤 + 验证基线）
```

- `issue.md` 状态机：`open → investigating → decided → implementing → verified → closed`
- 线索编号单调递增，新线索永远追加（`005-...`），保证可追溯

### index.md — 索引摘要（每轮唯一必读）

多轮接力的上下文成本控制靠它：**每轮只读 index.md**，详细文件按需定位。index.md 必须保持轻量（50 行内）：

1. **当前状态**：状态机当前值 + 所处阶段（现象收集 / 原因确认 / 方案制定 / 修复实施 / 验证）
2. **时间线**：问题-原因-修复 三段式，每段一行：`| 日期 | 阶段 | 摘要 | 进展核实 | 详见 |`
   - 摘要一句话（现象 / 确认的原因 / 修复方式）
   - 进展核实标注该段结论的核实方式（用户确认 / 代码对照 / bench 数据）
3. **下一步**：当前轮之后该做什么（等什么输入、验证什么假设、实施哪一步）
4. **入口指针**：issue / facts / hypotheses / decisions / plan 路径，按需读取

每轮结束前必须更新 index.md。交接时对方只读 index.md 起步，按指针按需加载，不碰线索全文。

### 分段推进与阶段性保留

设计假设：**当前轮可能无法一次解决**（缺权限、信息分批到、会话长度限制）。每个阶段性进展都保留为可独立核实的成果：

| 阶段 | 保留成果 | 核实方式 |
|------|---------|---------|
| 现象收集 | 线索文件 + 用户确认过的现象描述 | 用户 / issue 核实 |
| 原因确认 | facts.md 确认项（附代码位置） | 代码对照 / 复现 |
| 方案制定 | plan.md（量化目标 + 验证方式） | 评审 / grill-me |
| 修复实施 | 改动记录（文件 / 函数 / 验证命令） | 测试 + code-review |
| 验证 | bench 前后对比数据 | 数据闭环 |

阶段完成即更新 index.md 时间线。即使本轮中途停止，下轮或他人也能从时间线接续——**接续成本只有读 index.md**。

## 接力与重放

最终交付物是一个**可重放的修复包**，不依赖会话上下文：

- `index.md` — 时间线（问题-原因-修复）+ 核实状态
- `plan.md` — 可执行修复步骤：每个修复含涉及文件 / 函数、改动方式、依赖顺序、验证命令、基线数据
- `facts.md` — 确认的事实与验证基线（bench 数据）

交接场景：

1. **同仓库接力**：新会话读 index.md → 按 plan.md 继续实施 / 验证
2. **其他分支重放**：新 agent 在其他分支（feature / backport）按 plan.md 步骤 + 验证命令重放修复——步骤必须自包含，不引用本会话说过但未落盘的任何话；每个步骤写全：改哪里、改成什么、怎么验证
3. **人员交接**：index.md 时间线即交接报告，附 issue.md 业务背景

**重放校验标准**：一个新 agent 只读 `.issue/` 内文件（不读本会话记录），能否独立完成修复并跑通验证？不能，则 plan.md 写得不完整。

## 事实与推断分离（贯穿始终的纪律）

| 事实（facts.md） | 推断（hypotheses.md） |
|----------------|---------------------|
| 有来源、有线索编号、可复核 | 假设、猜测、交叉验证结论 |
| 日志行、指标值、代码行、用户原话 | "疑似"、"可能"、"结合 A 和 B 推测" |
| 不被后续讨论推翻，只被新证据修正 | 置信度随验证升降 |

**规则**：
- 推断不能冒充事实——无证据编号的表述一律进 hypotheses
- 从推断到事实需要一次验证动作（复现 / profiler / 确认代码路径）
- 代码对照结论（"该处实现为 X，与现象吻合"）可升级为事实，附代码位置

### 历史信息可信度（默认低可信）

**开发者提供的口述历史默认不可信**：记忆偏差、版本混淆、他人改动未同步认知，都可能造成错漏。

- "之前是这么实现的"、"上次改了 X" 这类表述，只作为**待核实线索**（hypotheses 或线索文件标注 `low-confidence`），不经代码对照 / 复现核实不得升级为事实
- **不修改历史**：发现矛盾时，历史线索原样保留，以追加形式记录修正（如 `clues/005-history-correction.md`：开发者称 X，代码对照显示 Y）
- 历史信息是"反馈"而非"事实"——它的价值在于引导核实，不在于直接采信

### 根因逐步逼近（feedback-driven convergence）

**事实根因不是一次敲定的**，而是随每轮反馈（新证据、代码对照、复现结果、用户核实）渐进收敛的结果。

facts.md 中每条根因/确认项带三个字段：

| 字段 | 含义 |
|------|------|
| 置信度 | 百分比，随反馈升降 |
| 支撑证据 | 线索编号列表（追加不删除） |
| 最近核实 | 最后一次反馈核实的日期与方式 |

每轮反馈更新置信度：新证据支撑则升级，矛盾证据则降级并记录矛盾线索。根因状态机：`候选 → 部分验证 → 高置信 → 最终根因`。

**最终根因判定（三重确认，缺一不可）**：

1. **多源独立信号指向同一处**（线索交叉验证）
2. **代码对照确认**实现与根因吻合
3. **与所有已知反馈无矛盾**（含用户核实）

宣告"最终根因"后才可进入决策阶段。之后若出现新反馈，根因结论允许被重新评估——**结论可推翻，历史不可改**。

## 输入通道（每轮）

用户可按任意组合提供：

1. **约定目录**：日志 / metrics 导出文件放入 `.issue/`（如 `.issue/logs/`），自动扫描
2. **临时指定路径**：`trace-to-plan 日志在 /tmp/app.log，先看下昨晚的报错`
3. **直接粘贴**：错误信息、trace 片段、指标数值、慢请求样例
4. **现象口述**：什么时候慢、多慢、影响谁、是否偶发

每类输入都整理为一条线索（`clues/NNN-*.md`），附来源、时间窗口、原始内容。

## 阶段 0：多边信号收集

四类信号，缺一不可——**单源是线索，多源交叉才升级为候选**。

| 信号源 | 采集要点 |
|--------|---------|
| **现象描述** | 用户/issue 怎么说：什么时候、多慢（数字）、影响谁、是否偶发；区分主观感受与客观指标（"感觉卡" vs "P99 从 200ms 到 2s"） |
| **trace 日志** | 慢调用链（span 耗时、跨服务链路）、错误/超时/重试风暴、反模式日志（N+1、循环内 I/O）、问题时段日志聚集 |
| **metrics 指标** | 延迟（P50/P95/P99 趋势）、吞吐、错误率、CPU/内存/GC/连接池/队列积压；问题时段 vs 正常时段、发布前后对比、峰值形态（尖峰/阶梯/周期） |
| **项目代码** | 热点路径、复杂度（O(n²)、全表扫描、锁竞争）、缓存缺失、无界增长、跨服务调用深度 |

## 阶段 1：信号收敛（每轮增量）

对每个新线索标注：**证据强度**（S0 猜测 / S1 单一证据 / S2 可复现 / S3 已量化）× **影响面**（用户感知 × 频率 × 范围）。

### 交叉验证规则

- **两个以上独立线索指向同一位置 → 升级为候选问题**（进 hypotheses，标置信度）
- 信号越多、越独立（不同来源，非同一日志的重复行），置信度越高
- 单线索不升级——它是线索，留在 clues/ 待更多证据

### 代码对照（优先动作）

每个新线索落库后，**立即用代码搜索工具对照实现**（grep / codegraph / read_file），确认或排除：

- 线索指向的代码路径是否真的存在？调用链是否如日志所示？
- 实现是否与现象吻合（如日志报超时，代码里该处是否真有无界等待）？
- 对照结论写入线索文件或 facts.md（附代码位置）——这是把"现象"变成"缺陷"的关键一步

每轮结束时更新候选清单排序（证据 × 影响）。候选通常 3-8 个，多于 8 个说明收敛不足，下一轮补充信号。

## 阶段 2：验证与决策

### 最小确认（对每个候选）

- 能用复现就复现（调用 `diagnosing-bugs` 的反馈循环机制——先建红绿信号）
- 能用 profiler / 局部 bench 量化就量化（火焰图、query plan、计时 harness）
- 无法确认的：降级为"待观察"，标记不确定原因

### 决策：修 or 不修

**前提**：根因已通过三重确认收敛为"最终根因"（见"根因逐步逼近"）——未收敛的候选不得进入决策，继续收集反馈。

**ROI = 影响 × 频率 ÷ 改动风险**，且必须对照业务约束评估：

| 决策 | 条件 | 动作 |
|------|------|------|
| 修 | 高置信 + 高影响 + 低/中风险 | 进阶段 3 |
| 不修 | 影响可忽略，或风险远超收益 | 记录理由，关闭 |
| 延后 | 影响存在但改动大 / 信息不足 | 记录，留待后续 |

**业务约束优先**：方案不是技术最优，而是业务约束下的最优——该功能对业务的价值、改动由谁承担风险、SLA 要求、发布窗口。技术洁癖让位于业务收益；业务不感知的"优雅"不配进计划。

**典型陷阱（禁止）**：发现一堆问题就全修。小问题大改动的优先关掉，收益不明确的优先延后。

### 产出：决策记录

每个"修"或值得记住的"不修"决策写入 `decisions.md`（ADR 格式，三条件与模板见 `planning/grill-me/ADR-FORMAT.md`），附业务理由。

## 阶段 3：方案规划

对每个入选问题产出：

- **解决思路**：方案 + 预期效果（量化目标，如"P99 从 2s 降到 500ms"）+ **业务价值陈述**（解决后业务得到什么）
- **风险与副作用**：兼容性、行为变化、回滚难度
- **验证方式**：怎么证明修好了（同一 bench 场景对比）

### 依赖分析

- **共享热点的问题先做**——修一处多处受益，且避免重复触达同一模块
- 标注修复间依赖：A 修完 B 才能测（如先拆慢查询才能并行化）
- 独立问题可并行

### 产出：实施计划

排序后的修复清单（问题 → 方案 → 风险 → 验证 → 依赖 → 业务价值），写入 `.issue/plan.md`，可直接作为 `sdd-spec` 的输入。

## 阶段 4：bench 闭环

- **修前 baseline**：量化记录当前指标（延迟/吞吐/资源占用，同一场景）
- **实施**：交给 `sdd-implement` 逐项实现
- **修后对比**：同一 bench 场景、同一数据量
- **回归**：功能不受影响（复用 `code-review` 双轴验证）
- 更新 `issue.md` 状态至 `verified` / `closed`

未做修后对比的问题不算完成——性能工作没有"凭感觉好了"。

## 协作关系

```
trace-to-plan（发现+决策，.issue/ 重入）
   ├─ diagnosing-bugs  阶段 2 单点深挖（红绿反馈循环）
   ├─ codegraph / grep  阶段 1 代码对照（实现验证）
   ├─ sdd-spec / sdd-implement  实施计划下游（spec + 逐票实现）
   ├─ code-review  变更后双轴验证（Standards + Spec）
   └─ grill-me  方案评审（可选，兼维护领域模型文档）
```
