# Trace to Plan — 从痕迹到计划

**定位**：wayfinder 的反向。wayfinder 从目标自顶向下规划（空白工程，决策 tickets 地图 → 逐票解决）；本 skill 从现状自底向上发现（存量系统）——多边信号 → 收敛候选 → 验证决策 → 方案规划 → bench 闭环。

空白工程极少，存量改造是常态。本 skill 回答三个问题：

1. **哪里有坑** — 多源信号交叉收敛出高置信候选问题
2. **值不值得修** — ROI 决策，不是发现的问题都该修
3. **怎么修最顺** — 排序、依赖、验证方式齐备的实施计划

## 适用场景

- 现有系统出现性能问题或缺陷：慢、卡、高 CPU/内存、错误率上升、偶发超时
- 已有现象描述、日志、指标，但没定位到具体缺陷
- 想知道"哪里值得改"以及"怎么改最有价值"
- 一次处理多个疑似问题，而不是单点 debug

单点明确 bug 深挖用 `diagnosing-bugs`；本 skill 负责"先发现哪些点值得深挖"。

## 阶段 0：多边信号收集

四类信号，缺一不可——**单源是线索，多源交叉才升级为候选**。对每个信号记录：来源、时间窗口、原始证据（日志行 / 指标值 / 代码位置）。

### 信号源 1：现象描述

- 用户/issue 怎么说：什么时候慢、多慢（数字）、影响谁、是否偶发
- 与"正常时"的对比参照
- 区分主观感受与客观指标（"感觉卡" vs "P99 从 200ms 到 2s"）

### 信号源 2：trace 日志

- 慢调用链（分布式追踪：span 耗时分布、跨服务链路）
- 错误/超时/重试风暴（日志中的异常聚合、同错误出现频率）
- 反模式日志证据：N+1 查询、循环内 I/O、重复计算
- 时间戳对齐：问题时段内的日志聚集

### 信号源 3：metrics 指标

- 延迟（均值/P50/P95/P99 趋势）、吞吐、错误率
- 资源：CPU、内存、GC、连接池、队列积压
- 时间窗口对比：问题时段 vs 正常时段；发布前后对比
- 异常峰值：尖峰、阶梯增长、周期性波动

### 信号源 4：项目代码

- 热点路径静态理解：请求链路、核心循环、高频调用点
- 复杂度审查：O(n²) 循环、全表扫描、锁竞争、串行化
- 缓存缺失/未命中、重复请求、无界增长
- 架构层：共享热点模块、同步阻塞点、跨服务调用深度

## 阶段 1：信号收敛

对每个信号标注两个维度：

- **证据强度**：S0 猜测 / S1 单一证据 / S2 可复现 / S3 已量化
- **影响面**：用户感知 × 发生频率 × 影响范围

### 交叉验证规则

- **两个以上独立信号指向同一位置 → 升级为候选问题**
- 信号越多、越独立（不同来源，非同一日志的重复行），置信度越高
- 单信号不升级——它只是线索，进"待观察"区

### 产出：候选问题清单

按 [证据强度 × 影响面] 排序。每项包含：

| 候选 | 指向它的信号 | 置信度 | 初步怀疑根因（标注猜测与否） |
|------|------------|--------|--------------------------|

候选通常 3-8 个，多于 8 个说明收敛不足，回阶段 0 补充信号。

## 阶段 2：验证与决策

### 最小确认（对每个候选）

- 能用复现就复现（调用 `diagnosing-bugs` 的反馈循环机制——先建红绿信号）
- 能用 profiler / 局部 bench 量化就量化（火焰图、query plan、计时 harness）
- 无法确认的：降级为"待观察"，标记不确定原因

### 决策：修 or 不修

**ROI = 影响 × 频率 ÷ 改动风险**

| 决策 | 条件 | 动作 |
|------|------|------|
| 修 | 高置信 + 高影响 + 低/中风险 | 进阶段 3 |
| 不修 | 影响可忽略，或风险远超收益 | 记录理由，关闭 |
| 延后 | 影响存在但改动大 / 信息不足 | 记录，留待后续 |

**典型陷阱（禁止）**：发现一堆问题就全修。小问题大改动的优先关掉，收益不明确的优先延后。

### 产出：决策记录

每个"修"或值得记住的"不修"决策，用 ADR 格式记录（`docs/adr/NNNN-*.md`，三条件与模板见 `planning/grill-me/ADR-FORMAT.md`）：难逆转 / 无上下文会惊讶 / 真实权衡。多数性能决策其实是"修了什么、为什么"，一两句即可。

## 阶段 3：方案规划

对每个入选问题产出：

- **解决思路**：方案 + 预期效果（量化目标，如"P99 从 2s 降到 500ms"）
- **风险与副作用**：兼容性、行为变化、回滚难度
- **验证方式**：怎么证明修好了（同一 bench 场景对比）

### 依赖分析

- **共享热点的问题先做**——修一处多处受益，且避免重复触达同一模块
- 标注修复间依赖：A 修完 B 才能测（如先拆慢查询才能并行化）
- 独立问题可并行

### 产出：实施计划

排序后的修复清单（问题 → 方案 → 风险 → 验证 → 依赖），可直接作为 `sdd-spec` 的输入（写入 `.plan/` 或转成 spec + 任务拆解）。

## 阶段 4：bench 闭环

- **修前 baseline**：量化记录当前指标（延迟/吞吐/资源占用，同一场景）
- **实施**：交给 `sdd-implement` 逐项实现
- **修后对比**：同一 bench 场景、同一数据量
- **回归**：功能不受影响（复用 `code-review` 双轴验证）

未做修后对比的问题不算完成——性能工作没有"凭感觉好了"。

## 协作关系

```
trace-to-plan（发现+决策）
   ├─ diagnosing-bugs  阶段 2 单点深挖（红绿反馈循环）
   ├─ sdd-spec / sdd-implement  实施计划下游（spec + 逐票实现）
   ├─ code-review  变更后双轴验证（Standards + Spec）
   └─ grill-me  方案评审（可选，兼维护领域模型文档）
```
