# .issue/ 目录约定与贯穿纪律（全量）

> 由 SKILL.md 引用。这是调查状态的完整布局与纪律细则；SKILL.md 只保留浓缩版。

## 目录结构

调查状态存于项目根 `.issue/`（或用户指定目录）。多问题并行时用子目录：`.issue/<slug>/`。

```
.issue/
├── index.md            # 索引摘要（每轮唯一必读）：时间线 + 状态 + 下一步 + 入口指针
├── issue.md            # 问题主档：现象描述、业务影响、当前状态
├── clues/              # 线索链：每条证据一个文件，递增编号，只追加
│   ├── 001-user-report.md       # 现象描述（用户原话/issue 摘录）
│   ├── 002-error-log.md         # 日志/trace 证据（原始行 + 时间窗口）
│   ├── 003-metrics.md           # 指标证据（数值、趋势、对比基线）
│   └── 004-code-spot.md         # 代码位置证据（文件:行 + 实现摘录）
├── facts.md            # 已确认事实（可复核，每项带来源线索编号）
├── hypotheses.md       # 推断与候选问题（标置信度，与事实严格分离）
├── decisions.md        # 决策记录（修/不修/延后，ADR 格式）
└── plan.md             # 实施计划（可重放修复步骤 + 验证基线）
```

- `issue.md` 状态机：`open → investigating → decided → implementing → verified → closed`
- 线索编号单调递增，新线索永远追加（`005-...`），保证可追溯

## index.md — 索引摘要（每轮唯一必读）

多轮接力的上下文成本控制靠它：**每轮只读 index.md**，详细文件按需定位。保持轻量（50 行内）：

1. **当前状态**：状态机当前值 + 所处阶段（现象收集 / 原因确认 / 方案制定 / 修复实施 / 验证）
2. **时间线**：问题-原因-修复 三段式，每段一行：`| 日期 | 阶段 | 摘要 | 进展核实 | 详见 |`
   - 摘要一句话（现象 / 确认的原因 / 修复方式）
   - 进展核实标注该段结论的核实方式（用户确认 / 代码对照 / bench 数据）
3. **下一步**：当前轮之后该做什么（等什么输入、验证什么假设、实施哪一步）
4. **入口指针**：issue / facts / hypotheses / decisions / plan 路径，按需读取

每轮结束前必须更新 index.md。交接时对方只读 index.md 起步，按指针按需加载，不碰线索全文。

## 事实与推断分离

| 事实（facts.md） | 推断（hypotheses.md） |
|----------------|---------------------|
| 有来源、有线索编号、可复核 | 假设、猜测、交叉验证结论 |
| 日志行、指标值、代码行、用户原话 | "疑似"、"可能"、结合 A 和 B 推测 |
| 不被后续讨论推翻，只被新证据修正 | 置信度随验证升降 |

规则：

- 推断不能冒充事实——无证据编号的表述一律进 hypotheses
- 从推断到事实需要一次验证动作（复现 / profiler / 确认代码路径）
- 代码对照结论（"该处实现为 X，与现象吻合"）可升级为事实，附代码位置

## 历史信息可信度（默认低可信）

**开发者提供的口述历史默认不可信**：记忆偏差、版本混淆、他人改动未同步认知，都可能造成错漏。

- "之前是这么实现的"、"上次改了 X" 这类表述，只作为**待核实线索**（hypotheses 或线索文件标注 `low-confidence`），不经代码对照 / 复现核实不得升级为事实
- **不修改历史**：发现矛盾时，历史线索原样保留，以追加形式记录修正（如 `clues/005-history-correction.md`：开发者称 X，代码对照显示 Y）
- 历史信息是"反馈"而非"事实"——它的价值在于引导核实，不在于直接采信

## 分段推进与阶段性保留

设计假设：**当前轮可能无法一次解决**（缺权限、信息分批到、会话长度限制）。每个阶段性进展都保留为可独立核实的成果：

| 阶段 | 保留成果 | 核实方式 |
|------|---------|---------|
| 现象收集 | 线索文件 + 用户确认过的现象描述 | 用户 / issue 核实 |
| 原因确认 | facts.md 确认项（附代码位置） | 代码对照 / 复现 |
| 方案制定 | plan.md（量化目标 + 验证方式） | 评审 / grill-me |
| 修复实施 | 改动记录（文件 / 函数 / 验证命令） | 测试 + code-review |
| 验证 | bench 前后对比数据 | 数据闭环 |

阶段完成即更新 index.md 时间线。即使本轮中途停止，下轮或他人也能从时间线接续——**接续成本只有读 index.md**。
