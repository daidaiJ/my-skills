# SDD Brainstorm — 轻量需求头脑风暴

用最少轮次帮用户理清需求、锁定方案，为写规格文档做准备。

## 核心原则

1. **先查后问** — 能从代码库得到答案的不问用户
2. **聚焦收敛** — 每轮有明确目标，不发散
3. **用户主导** — 用户随时可以说"够了，进入下一步"
4. **最小工具** — 能用 grep/read 解决的不调 LSP，能对话解决的不派子智能体

## 工作流程

### 第 0 步：前置条件检查（必做，L0）

开始讨论前，用 grep/read 快速扫描代码库：

1. 用户描述的功能是否已有部分实现？在哪些文件？
2. 项目技术栈（语言、框架、构建工具）
3. 涉及哪些现有模块和依赖
4. 测试现状和框架

整理成「前置条件摘要」展示给用户，确认准确性。

> 如果 `.plan/brainstorm.md` 已存在（上次讨论的残留），先读取并告知用户，避免重复工作。

### 第 1 步：需求澄清（1-2 轮对话）

聚焦 **What**：
- 解决什么问题？核心场景？（最多 3 个）
- 非目标（不做什么）？

每轮给出理解和建议，请用户确认。不连珠炮提问。

### 第 2 步：方案探索（1-2 轮对话）

聚焦 **How**：
- 提出 1-2 个可行方案，一句话概述 + 关键优劣
- 指出需要用户决策的关键点

用户已有方案时直接确认，不强行推销替代方案。

### 第 3 步：锁定结论

输出结构化摘要：

```markdown
## 需求摘要
- **目标**：一句话
- **用户场景**：核心场景列表
- **非目标**：明确不做的事

## 选定方案
- **方案**：一句话
- **关键决策**：已确认的技术决策
- **开放问题**：仍需确认的点（如有）

## 前置条件
- **涉及文件**：需修改的文件列表
- **依赖模块**：相关模块
- **约束**：已知技术约束
```

提示用户：

> 结论如上。接下来可以用 `/sdd-spec` 生成规格文档，或用 `/grill-me` 压力测试方案。

## 复杂度升级（按需，不默认触发）

| 信号 | 升级动作 | 何时值得 |
|------|---------|---------|
| 涉及 3+ 模块，方案不确定 | 进入 plan mode 做结构化探索 | 跨模块重构、架构选型 |
| 需要了解符号依赖关系 | 调 LSP `workspaceSymbol` / `findReferences` | 接口变更、影响面分析 |
| 方案需要领域建模 | 派发「软件架构师」子智能体 | 新领域、复杂业务规则 |

**判断标准**：如果 grep + 对话能在 3 轮内锁定方案，就不升级。升级是为了节省后续返工成本，不是为了流程完整。

## 输出

写入 `.plan/brainstorm.md`。

## 禁止

- 不自动生成规格文档（等用户要求）
- 不在头脑风暴阶段讨论实现细节
- 不一次性问超过 3 个问题
- 用户说"直接做"时跳过剩余步骤，输出已知信息
